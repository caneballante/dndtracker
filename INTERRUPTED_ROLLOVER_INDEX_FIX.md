## Diagnosis and invariants

The prior normal-rollover `onstop` flushed the old audio, then called `startRecorderCycle()` even if the microphone had ended/capture required recovery. That function constructed a recorder and advanced the durable next-index counter **before** calling `MediaRecorder.start()`. A synchronous rejection therefore consumed an index despite never beginning capture. Recovery then respected that counter and advanced again. This code defect is deterministically reproduced. It strongly matches the real session's ended track, scheduled old-tail save, absent index-2 start/emission, recovery at index 3 and final missing index 2.

The historical evidence does **not** contain the browser exception or exact reservation timestamp. Allocation would occur in the attempted replacement after the 4:20:11 rollover and before the 4:20:27 recovery. A constructor rejection alone occurs before allocation in this implementation, so would not itself explain the consumed index. A synchronous `start()` rejection versus an accepted start with absent `onstart` cannot be conclusively distinguished from the old metadata. Do not claim a recorded exact exception or additional lost audio.

Invariants: invalid rollover cannot begin another recorder; old final audio remains saveable; candidate allocation is distinct from accepted capture; accepted starts remain required even before `onstart`/first checkpoint; checkpoints and upload acknowledgments do not substitute for each other; missing accepted/server audio blocks completion; the original session and increasing used indexes remain intact.

## Small correction

- `dnd-audio.html`: checks live tracks, active stream, Stop/Pause and recovery-required state before a new cycle. A healthy rollover retains its immediate restart. The old tail is still queued before restart decisions.
- The recorder index remains an **ephemeral candidate** until `start()` returns successfully. A constructor/start rejection creates no durable reservation and no recorded chunk to reuse, renumber or tombstone. Accepted start immediately advances the in-memory and durable next-index counter in the same synchronous call, before asynchronous browser callbacks can run. This relies on the [MediaRecorder method contract](https://www.w3.org/TR/mediastream-recording/#dom-mediarecorder-start): state changes synchronously, events dispatch asynchronously. A rejected start is not a successful capture attempt. Startup failure is surfaced through existing recovery/recorder error handling.
- Accepted-start and delivered-stop markers distinguish recorder lifecycle from audio emission. Recovery waits for an old accepted recorder's outstanding final callback, but does not wait for another `onstop` after one already arrived. Late old audio still retains its original index/session.
- Stop's expected boundary includes all accepted durable indexes and actual emitted audio, including restored reservations. A started recorder with no checkpoint/audio remains a missing integrity issue. Unknown old reservations are not reused or silently excused. Normal Stop's late-data drain barrier remains in place.
- Delayed ordinary/recovery `onstart` cannot override Stop/Pause. Its final data still saves.
- `session_evidence.py`: finalization verifies actual audio-file presence instead of treating a status acknowledgment as proof that the file still exists. The contiguous expected-index barrier is unchanged. A regression showed the old implementation incorrectly advanced an acknowledged-but-absent audio file to waiting-for-transcription; it now waits for that missing upload. Existing reconciliation/reference test fixtures now create synthetic WAV files rather than metadata-only audio claims. No AI model/prompt/notes/Session Memory behavior was changed.
- `capture-reliability.js` and the interruption panel retain a compact stage history across requested, microphone reconnecting, recorder starting/started and durable checkpoint. Recovery is not delayed. Failed/cancelled attempts retain their actual current failure text; a new attempt resets its history.

No abandoned-index mechanism or server exemption was introduced. Existing historical phantom index 2 remains blocking; changing it would require separate evidence and authorization. No empty WAVs were fabricated or saved chunks renumbered.
